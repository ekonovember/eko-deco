# Runtime cards — the printed wetnotes format

Print-ready 90 × 64 mm (landscape) runtime cards, generated by
[`deco.cards`](../src/deco/cards.py) from numbers produced by `deco.cli`.

The engine lives in the package (DECISIONS #31) — the printed card is a product
surface, so it ships in the wheel under the `[gui]` extra. This directory is the
workspace: this format reference, the vendor citation in `reference/`, and
`make_scenario.py`, a driver for the two `examples/scenario_*` dives.

```bash
python -m deco.cards          # the EXAMPLE card (.pdf + .png) into the cwd
python cards/make_scenario.py # the two scenario dives, into cards/
```

## Printing — use `print_a4.pdf`

The single-card PDFs really are 90 × 64 mm (MediaBox 255.12 × 181.42 pt), but
printers and PDF viewers default to **fit to page**, which scales that little
page up to a full A4 sheet. Turning scaling off in the print dialog works, but
it is one forgotten checkbox away from a useless print.

`print_a4.pdf` avoids the problem: an A4 page holding 4 copies of each card at
exact size with crop marks, plus the reminder printed in the margin. A4 is the
paper size, so "fit to page" has nothing to scale — print it, cut on the card
borders. Cards sit 11 mm from the page edges, crop marks 4 mm outside that, so
it survives any normal printer's unprintable margin.

Keep the single-card PDFs for a print shop or a plotter that honours exact page
sizes; use the A4 sheet everywhere else.

## The format, and why it is that format

This is not a house style: it is the convention every planner and every slate
runtime has converged on. Verified 2026-08-01 against the sources below,
and re-verified 2026-08-05 against two full MultiDeco exports (`../examples/`).

| Rule | Why |
|------|-----|
| **One row per stop**, columns `DEPTH · GAS · STOP · RUN` | The MultiDeco-X1 plan screen prints exactly this: `3m 12 70 rt` = depth / stop minutes / runtime. `rt` (runtime) is the load-bearing number. |
| **Rows in ascent order**, deepest first, last row `SURF` | You read *down* the card as you come up. |
| **RUN is cumulative and is the time you LEAVE that stop** | Not when you arrive: arrival + hold = RUN. Matches `bottom_time`/`Level.runtime` in this repo, and MultiDeco/GFDECO/Subsurface. |
| **Every stop row carries its own runtime**, not just a TTS at the foot | MultiDeco prints `3m 12 70 rt` — depth, stop minutes, runtime — on *each* line, because a diver flies the ascent off the runtime clock, not off a stopwatch restarted at every stop. In the contingency grid each cell is therefore `stop/run`. A card with stop times alone forces mental arithmetic at 6 m. |
| **STOP is the leg, not the hold** — the ascent to that stop plus the time held there, measured from the previous stop | So the STOP column always adds up to the RUN column. MultiDeco prints it this way: in `examples/scenario_2` the 9 m row reads `5:00` and the runtime goes 46 → 51, a 0:20 ascent plus a 4:40 hold. Printing the hold alone leaves the two columns irreconcilable and a diver adding STOP up surfaces one ascent early *per stop* — see [DECISIONS.md](../DECISIONS.md) #17. Defined once in `buhlmann.stop_legs`; the GUI's stop table and the contingency cut table render the same numbers. |
| **A gas-switch row is an annotation** | It carries the runtime the switch happens at, but the stop legs are not measured from it — otherwise a view that shows switches and one that doesn't would print different minutes for the same stop. |
| **The first stop is padded so the runtime lands on a whole minute** | MultiDeco's `0:27` rows (9 m in `examples/scenario_1`, 18 m in `examples/scenario_2`) are exactly that padding, not an obligation — after it every leg is a whole minute. eko-deco does not pad; it truncates instead, which costs at most the same minute in the same direction. |
| **Runtimes truncated to whole minutes** | MultiDeco's own convention — `report.runtime_min`, verified against a real export (`43.875 → 43`) and re-confirmed by both exports in `examples/` (`41.22 → 41`, `42.56 → 42`). Never round up a runtime; round *TTS* up. |
| **TTS on the last line** | Modern computers moved the emphasis from fixed runtimes to TTS; it is what you compare against the computer in the water. |
| **Gas switches named in the row where they happen** | `sw` + the mix in the GAS column at the switch depth. |
| **Contingencies as parallel columns, not a second card** | The standard trio is *deeper* (next 3 m step), *longer* (+3–5 min) and *lost deco gas*. MultiDeco's own scenario table uses columns `OK / lost 50 / lost 100 / both lost` — see `tests/shearwater_golden.json` (`_multideco_provenance` from screenshots, `_scenario_provenance` from the two full exports in `examples/`). |
| **Drop the contingency axes the site cannot produce** | The current dive is a shot line to a fixed 32 m bottom, then a wall: the depth cannot be overrun, only the bottom time. So the cards carry bottom-time columns (20/23/26/29 min) and no depth axis — a column a diver can never hit is wasted plate. Re-add the depth axis for a site where it is reachable. |
| **End-of-stop pressure as ONE grey `bar` column, for the planned column only** | The pressure you should see leaving each stop is the single gas figure an SPG can check underwater — the card says 197 bar leaving 21 m and the needle either agrees or the dive has changed. It is drawn for the *planned* scenario only and set in grey: the columns on this card are contingencies, and four sets of pressures would take the width that makes the runtimes readable, while on a lost-gas column the pressures below the switch no longer apply anyway. `deco.cards.bars_from_plan` takes them from `deco plan --json` (`stops[].end_bar`, computed once in `report.leg_pressures`), so the card cannot drift from the gas report. Blank on the bottom row — you leave the bottom, you do not hold on it — and blank for any mix carrying no cylinder. |
| **Gas plan beside the table**: need / have, min gas, turn pressure | Divers record "estimated gas needs versus available supply", min gas and lowest team MOD alongside the schedule. MultiDeco notes its own volumes carry **no reserve** — ours add rock bottom explicitly. |
| Header carries model + GF + water + rates + mixes | Reproducibility: a card you cannot re-derive is a card you cannot trust. |

Layout of the two current cards: title bar, then two contingency tables side by
side — **ON PLAN** and **LOST deco gas** — sharing the same bottom-time
columns. Each cell is `stop/run`; `SUR` and `TTS` close each table. A bold
min-gas + turn-pressure line and one small line of cylinder pressures finish
the card.

**The schedule numbers get the space.** They are set at 7.4 pt — read at arm's
length through a flooded mask, in gloves — and everything else is subordinate
to that. Off the card went the model name (`ZHL-16C`), the descent rate and the
whole cylinder/rate strip: reproducibility metadata, not things you act on
underwater. GF lives in the title bar, per-cylinder pressures on the small
bottom line, min gas and turn pressure on the bold line above it. If something
new has to go on a card, take the space from the footnotes, never from the
table.

Table drawing is a real grid, not padded monospace text (`table()` in
`deco.cards`): fixed column centres, every cell formatted to exactly five
characters so the `/` lines up down each column, single values (`SUR`, `TTS`)
padded to sit under the runtime digits, zebra banding on the stop rows so a
depth stays trackable across four columns, and rules closing the header, the
stop block and the foot. Row pitch follows the type size, so changing `size=`
re-spaces the table instead of overlapping it.

## Levers left, if a card needs to grow

Recorded so the next person does not rediscover them. In the order to spend
them:

1. **V1 has a blank band under its table** (V2 spends that space on the NDL
   strip). Passing a larger `size=` to `table()` for V1 alone takes the grid to
   about 8.5 pt; the row pitch follows the size, so nothing else needs moving.
   Left blank on purpose for now — it is pencil space on a wetnotes card.
2. **Drop the LOST table on V2.** Its stops differ from the on-plan table by
   1–2 min, so it is the least load-bearing thing on either card; removing it
   frees the full width and takes the remaining grid to roughly 10 pt.
3. **Drop the `29` column.** +45 % over planned bottom time is already generous
   for a fixed-depth wall dive; three columns widen everything by a third.
4. Only then start cutting the footnote lines — they are already the smallest
   type on the card and cost the least.

Do **not** buy space by shrinking the schedule grid, by dropping the per-stop
runtimes back to a bare TTS, or by re-adding a 2-D depth × time cut table.

## Building a card from a plan — don't transcribe

`deco.cards` computes nothing, but it no longer needs you to copy numbers by
hand, which is where a card drifts from its schedule:

```python
import json, subprocess
from deco import cards as mc

def plan(**kw):                      # one deco plan --json per column
    ...
cols = [plan(time=t) for t in (20, 25, 30, 35)]
rows = mc.rows_from_scenarios(cols)   # one column per plan, left to right
```

`rows_from_scenarios` reads the `stops` key, which already carries the printed
notation resolved — the **leg** and the **leave-at runtime** — so a cell cannot
end up holding a raw hold copied out of the CLI's segment table. `gas_line`
derives the switch depths from the same plan. `tests/test_cards_format.py`
pins that a card cell equals `buhlmann.stop_legs`, and that the card, the GUI's
runtime card and the contingency cut table all print the same numbers.

Type size auto-fits the row count (`fit_size`): the layout was first drawn
around three stops, and a real trimix schedule has seven, which used to write
the TTS row straight over the summary.

## The hand-written variant, and what it fixes

A diver's own wetnotes card for `../examples/scenario_2`, photographed
2026-08-05, uses a tighter notation than the printed one. It is recorded here
because it is evidence of how a schedule gets written **by hand**, which is a
different question from how a planner prints one:

```
        RT
  ↓  32   4   (4)
  —  32  36  (40)
  ↑  21   1  (41)
  ↑  18   1  (41)  ▼
  —  18   1  (42)
  —  15   2  (44)
  —  12   2  (46)
  —   9   5  (51)
  —   6   5  (56)  ▼
  —   3  10  (66)
```

`↓` descent · `—` held · `↑` ascent, then depth, **leg** minutes, and the
runtime **in brackets**. `▼` in the margin marks a gas switch.

Three rules worth carrying into any printed card:

1. **The runtime is bracketed and the leg is not.** Two numeric columns that
   could be confused are separated by punctuation rather than by a header —
   on a wetnotes card there is no room for headers.
2. **Every row carries a direction glyph**, so a transit row and a held row are
   distinguishable at a glance underwater. This is the part a planner export
   does *not* give you: MultiDeco says `Wynurz.do` / `Przyst. na` in words,
   which does not survive being copied onto a slate.
3. **A gas switch is a margin mark, not a row.** It annotates the row it happens
   on; it is not measured from and gets no line of its own — the same rule as
   `buhlmann.StopLeg` and DECISIONS #17.

Every row of it matches `../examples/scenario_2/data.txt` exactly, including
the two rows that share runtime `(41)` (the 21 → 18 m transit is under a
minute, so the truncated runtime does not advance) — copied faithfully rather
than "fixed", which is the right instinct. Legs are rounded to whole minutes
(`36` for `35:59`, `1` for `0:27`) while the runtime column stays exact: the
same priority `report.runtime_min` encodes.

**No dive-specific card lives here.** `deco.cards` is the engine;
cards are made per dive, rendered from `deco plan --json`, and the PDFs are
gitignored. Don't commit a plan back into this directory.
